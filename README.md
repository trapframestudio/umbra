# Umbra

**Umbra: a S.T.A.L.K.E.R. G.A.M.M.A. modpack.** It is G.A.M.M.A. with xrRazom
co-op, a set of extra mods and Zone Gore Overhaul (with its baked character
models) on top, set up and tested together. Play it alone or in co-op.

One installer, for Windows and Linux, puts it all in place. It installs
G.A.M.M.A. or adds Umbra to the G.A.M.M.A. you already have, makes its own
Mod Organizer 2 profile and adds Umbra to Steam. Steam's "Umbra" opens the
Umbra launcher: Play, the season, updates and repair, with Mod Organizer 2 a
button away. Players can still add, turn off and reorder mods in MO2 as usual.

- **G.A.M.M.A.** is pinned to the version Umbra was tested with, and installed
  by FaithBeam's stalker-gamma-cli.
- **xrRazom** (co-op) follows its latest release.
- **The Umbra layer** is everything else: xrRazom, the extra mods, Zone Gore
  Overhaul and its bake. Umbra hosts these itself, crediting every author,
  except xrRazom: its author asks that it be downloaded from ModDB (so its
  downloads are counted), so players' Setup downloads it there.

The player picks a season for C Consciousness's grass and trees (spring,
summer, autumn or dead winter; autumn by default) and can switch in the
launcher (or by running Umbra Setup again). Every pick is remembered, so an
update never changes them.

Planned: optional 4K character textures.

## How a pack is defined

`pack/umbra.toml` describes one version of Umbra:

- `[pack]`: name, version, and channel (`stable` or `testing`).
- `[hosting]`: the base URL the pack is published at. It is built into the
  installer.
- `[source]`: the tested MO2 instance and profile the pack is built from.
- `[gamma]`: the stalker-gamma-cli release (URL and sha256 for each
  platform), the G.A.M.M.A. git repositories at the commits Umbra was tested
  with, and the G.A.M.M.A. lists in `pack/gamma/`.
- `[profile]`: the MO2 profile the installer makes ("Umbra", based on
  "G.A.M.M.A"). Its load order is the tested profile's, snapshotted at build
  time; `drop` removes entries.
- `[[layer]]`: one per mod, highest priority first. `folder` is the MO2 mod
  folder. `target = "anomaly"` copies into the Anomaly folder instead (that is
  how xrRazom's `bin/` is installed). `archive` takes the files from a zip,
  or `source` from a pinned `[sources.<id>]` archive (zip or 7z; a 7z is
  unpacked once into `~/.cache/umbra-src/unpacked`). `from` takes a folder
  from elsewhere (the source folder when it has another name), and `files`
  adds single files on top of it. `without_files_of` leaves out every file
  other layers have. `was` lists the folder's earlier names: Setup renames an
  installed one instead of installing it again beside it. `credit` names an
  entry in `credits.toml`.
- The **Umbra mod** (`folder = "Umbra"`) is Umbra's own changes in one mod:
  the tuned MCM values and the look from `look/` (splashes, fonts, the UI
  repaint, text). It overrides only what Umbra changes, so G.A.M.M.A.'s UI
  stays underneath; see `look/README.md`. Run `python3 look/layer.py` before
  a pack build when the look changed.
- A `[sources.<id>]` with `players_download = true` (and its `page` and
  `download` link) is never packed or uploaded: players' Setup downloads the
  author's archive itself. Its layers say what they take from it, in order, a
  later pair winning, as a fomod does: `take = [["gamedata/", "gamedata/"],
  ["gamma/gamedata/", "gamedata/"]]` is xrRazom's fomod for G.A.M.M.A., and
  `take = [["Anomaly/", ""]]` puts its `bin` and `gamedata` into the game
  folder, as its install notes say.
- `[[option]]`: optional parts the player can pick in the installer. A tick
  box (`default = true/false`): a layer with `option = "<id>"` is only
  installed when it is picked. Pick one (`choices`, `default` = a choice id):
  a layer with `option = "<id>=<choice>"` is installed for that choice.
  Layers of a choice the player moves away from stay on disk, switched off.

Every layer's `credit` must match an `id` in `pack/credits.toml`.

## How a pack is built

```
python3 dev/pack_build.py --dry-run     # what would be packed, plus a check for personal paths
python3 dev/pack_build.py               # build into dist/
python3 dev/pack_build.py --out DIR --volume-mb 1024 --jobs 8
```

Always run `--dry-run` first: it lists each layer's size and warns about any
file that still mentions your home folder. A full build needs about as much
free space as the pack itself (over 25 GB), so check the drive first.

The build packs each layer's folder as it is in the tested instance into zip
volumes of about `--volume-mb` (unpacked). MO2's hidden `*.mohidden` files are
left out and `meta.ini` is rewritten without local paths. The zips are
deterministic, so an unchanged layer gives the same files and a rebuild only
packs what changed. Linux programs and scripts (files starting `\x7fELF` or
`#!`, such as ZGO Setup's `zgo-setup-linux`) are packed `rwxr-xr-x` whatever
their mode in the instance, since an MO2 install drops mode bits, and Setup
installs them runnable. Zone Gore Overhaul is packed by its own release rules,
with its bake, and its version comes from `VERSION` in `zgo_main.script` (MO2
writes a date stamp such as `d2026.11.14` into its `meta.ini`). The bake must be
in the ZGO folder when you build: run ZGO Setup (or `zgo-setup.sh --bake --yes`)
for the instance's profile first, and check that `--dry-run` shows the zgo layer
at about 7.8 GB, not about 0.5 GB.

A rebuild under the same pack version with a changed layer (a rebake, a fix)
reaches installs too: Check for updates names the changed mods and offers
Update. Bump `[pack] version` for anything players should see as a release.

The output in `dist/`:

```
objects/<sha256>.zip|.txt    layer volumes, the G.A.M.M.A. lists, the Umbra load order
packs/umbra-<version>.json   the pack manifest
channels/<channel>.json      points at the manifest
CREDITS.md                   everyone whose work is in the pack
```

`dev/b2_upload.py` publishes `dist/`. `dev/build_installer/build.sh` builds the
installer programs into `dist/installer/`.

## How a pack is hosted

Everything lives under one base URL (a Backblaze B2 bucket, ideally behind
Cloudflare), and every file except the channel files is named by its sha256:

```
channels/<channel>.json   {"format": 1, "version": "...", "pack": "packs/umbra-<v>.json", "sha256": "..."}
packs/umbra-<v>.json      the pack manifest, checked against the channel's sha256
objects/<sha256>.<ext>    every file the manifest names, checked against its sha256
```

A channel file is the only thing that ever changes in place. Publishing a new
version uploads the new objects and the pack first, then switches the channel,
so players never see a half-published version. The manifest lists the pinned
G.A.M.M.A. (CLI, repository commits, lists), the Umbra profile's load order,
the options, every layer with its volumes, and the credits.
`installer/umbra_installer/packdef.py` documents the format in full.

The base URL can also be a local folder, for testing or for an offline copy.

## What the installer does

Players download one program: `Umbra-Setup-x86_64.AppImage` on Linux (make it
executable and open it; no FUSE 2 needed) or `Umbra Setup.exe` on Windows. Neither
needs anything installed. `dev/build_installer/README.md` explains how they're built.

```
umbra-setup                         the window
umbra-setup --install-to DIR        install G.A.M.M.A. and Umbra into an empty folder
umbra-setup --add-to MO2_DIR        add Umbra to a G.A.M.M.A. install you already have
  --source URL|DIR                  where the pack is published (built in for releases)
  --channel stable|testing          --no-steam     --proton NAME    --yes (don't ask)
  --with OPTION / --without OPTION  pick optional parts
  --with OPTION=CHOICE              pick one, e.g. --with ccon-season=winter
  --repair                          also reinstall any Umbra mod whose folder lost files
umbra-setup --plan ...              only say what would happen
umbra-setup --selftest              check that this program works here
umbra-setup --launcher [--work DIR] [-- STEAM_COMMAND...]   the launcher
```

First it shows a plan: what it will download, the space it needs, and anything
in the way (MO2, Steam or the launcher open, too little space, a folder that
isn't empty; on Linux, no Steam).

**New install.** Into an empty folder: stalker-gamma-cli installs G.A.M.M.A.
there (`anomaly/`, `gamma/` for MO2, `cache/`), then Umbra goes on top. The CLI
gets settings of its own, so a player's own stalker-gamma-cli setup is left as
it was (on Windows, Umbra adds its own CLI profile and switches back to the
player's afterwards).

**Adding to an existing G.A.M.M.A.** Point it at the G.A.M.M.A. MO2 folder.
G.A.M.M.A. itself is not touched; only the Umbra layer is added.

Either way, it then:

0. First of all, gets the mods whose authors ask that they be downloaded from
   their own page (xrRazom, from ModDB). It uses the copy in the player's
   Downloads folder if it's there (checked against its sha256). Otherwise it
   follows the page's download link and then its mirror link, as a browser does,
   which counts as a download there. If the site won't hand the file to a
   program (a Cloudflare check), the player's own browser opens the download
   link, the download starts there, and Setup carries on by itself once the
   file is in Downloads (or wherever the player says they saved it). This
   comes first so that it is settled before G.A.M.M.A.'s long install.
1. Downloads every volume and checks its sha256. Broken downloads resume. The
   cache is kept, so a repair or an update downloads only what changed.
2. Unpacks each layer into its MO2 mod folder, or into the Anomaly folder for
   xrRazom's engine. A mod the pack renamed is renamed in place first, keeping
   its place and on/off state in Umbra's profiles, so it isn't installed twice. A layer counts as in place only if its files still are
   (their sha256 is kept). A G.A.M.M.A. install or update puts G.A.M.M.A.'s
   own engine back over xrRazom's, and xrRazom's scripts then stop the game at
   load (`xrr_share_news_from` is nil). So Setup puts Umbra's back, and
   G.A.M.M.A.'s newer files become the originals that removing Umbra restores.
3. Makes an MO2 profile called "Umbra": a copy of G.A.M.M.A.'s profile with
   Umbra's load order. G.A.M.M.A.'s own profile is never changed. MO2 opens the
   Umbra profile from then on.
4. Gets what the game needs from Microsoft (see below).
5. Installs the launcher in the install's `.umbra` folder (see below), with
   the pack manifest (`pack.json`) it reads the options from.
6. Adds Umbra to Steam (see below).
7. Writes `UMBRA-CREDITS.txt` next to `ModOrganizer.exe`.

Everything it logs also goes to `.umbra/logs/setup-<date>-<time>.log` (the
newest 20 are kept), including the error if it fails.

Running it again is safe: finished steps are skipped and an update replaces
only the layers that changed.

**It never overwrites the player's folders.**

- It writes a mod folder only if the folder doesn't exist yet, or holds
  Umbra's marker (`umbra.layer.json`). If someone else's folder has the same
  name, the layer goes into `<folder> (Umbra)` instead.
- Before a layer replaces files in the Anomaly folder, it backs each one up to
  `<anomaly>/.umbra-backup/<layer>/`.
- A layer is unpacked into a temporary folder and moved into place only when
  every volume unpacked cleanly.

**Path relocation.** Some mods write absolute paths into their files (Zone
Gore Overhaul's bake report, for example). The build replaces the build
machine's paths with tokens, and the installer puts in the player's own:

| Token | Becomes |
|---|---|
| `@@UMBRA_MO2@@` | the MO2 folder, in the system's own form |
| `@@UMBRA_MO2_WIN@@` | the same as the game sees it (`C:\...`, or `Z:\home\...` under Wine/Proton) |
| `@@UMBRA_ANOMALY@@`, `@@UMBRA_ANOMALY_WIN@@` | the Anomaly folder, the same two ways |
| `@@UMBRA_ZGO_CACHE@@` | Zone Gore Overhaul's baker work folder |

Each token also has an `_ESC` form with doubled backslashes, for JSON and Lua
strings. The manifest lists which files of each layer carry tokens.

**Steam shortcut.** Umbra appears in the Steam library as a non-Steam game
that opens the Umbra launcher, with Umbra's icon and artwork. On Linux MO2
runs through Proton (`proton_experimental` unless `--proton` names another).
Steam must be closed while the shortcut is added, because Steam rewrites its
files when it exits; the installer waits for it. Steam's files are backed up
next to themselves (`*.umbra-bak`) first, and other shortcuts are kept.
`--no-steam` skips this step. Steam from Flathub only
sees its own folders, so Setup lets it reach the install with
`flatpak override --user --filesystem=<install> com.valvesoftware.Steam`.

**Start menu, applications menu and desktop** (`shortcuts.py`). Umbra also
starts without Steam: Setup puts the launcher in the Start menu and on the
desktop on Windows (`Umbra.lnk`, made with the shell's own ShellLink object, in
the player's own Programs folder: no admin), or in the applications menu
(`~/.local/share/applications/umbra-<id>.desktop`) and on the desktop
(`XDG_DESKTOP_DIR`, marked trusted for GNOME with `gio`) on Linux. A second
Umbra install is named after its folder ("Umbra (Other)"). `--no-shortcuts`
(or the tick in the window) leaves them out. The launcher's own Update, Apply
and Repair refresh the ones still there and never bring back one the player
deleted; an install from before this gets them on its next update. Setup's
state records them (`shortcuts`), for an uninstall.

On Linux, started from the menu, the launcher runs MO2 through Proton itself,
as Steam would, and Steam needn't be open:

1. Steam's own command from the last start through Steam
   (`.umbra/steam-launch.json`: the command without Steam's `reaper` and
   `steam-launch-wrapper`, and the `STEAM_COMPAT_*` and `PRESSURE_VESSEL_*`
   settings Steam gave Proton; never the account or the overlay);
2. else one made from Steam's files: the Proton the shortcut uses
   (`config.vdf` CompatToolMapping, else the one Setup picked, else Proton
   Experimental or the newest), found across every Steam library
   (`libraryfolders.vdf`, `compatibilitytools.d`), inside the Steam Linux
   Runtime its `toolmanifest.vdf` asks for (`require_tool_appid`, found by its
   appmanifest), in the shortcut's prefix (`steamapps/compatdata/<appid>`), or,
   for an install without a Steam shortcut, Umbra's own (`.umbra/proton`).

Both share the prefix with starts from Steam, so the first-start setup below
happens once either way.

**What the game needs from Microsoft.** Anomaly's engine loads the Visual C++
runtime (`msvcp140`, `vcruntime140_1`, `concrt140`), `d3dcompiler_47` and
`d3dx9_43`/`d3dx10_43`/`d3dx11_43`. Windows lacks some of them unless something
installed them, and Proton's Wine only has stand-ins, which the engine closes
on at once, without a log. Umbra gets them from Microsoft, pinned by sha256
(`runtime.py`): `vc_redist.x64.exe`/`vc_redist.x86.exe` (14.44), two Windows
SDK cabinets (`d3dcompiler_47`), and the `Microsoft.DXSDK.D3DX` NuGet package.

- **Windows:** when the Visual C++ runtime is missing or older than 14.40,
  Setup runs Microsoft's installer (`/install /quiet /norestart`); Windows asks
  for permission, and the plan says so beforehand. The D3DX DLLs (and
  `d3dcompiler_47`, where Windows lacks it) go next to the game's exe in
  `anomaly/bin`, which is how Microsoft ships D3DX now.
- **Linux:** Setup downloads and unpacks the DLLs (`.umbra/cache/runtime`).
  The prefix doesn't exist until Proton first runs for the shortcut, so the
  launcher finishes the job: before Play or Open MO2 it checks Steam's prefix
  for the shortcut (`STEAM_COMPAT_DATA_PATH`). The first time, it has Proton
  make the prefix (`cmd.exe /c exit` through Steam's own Proton command), puts
  the DLLs into `system32`/`syswow64`, and imports DLL overrides
  (`"*msvcp140"="native,builtin"` and so on) with Wine's `reg.exe`. This is
  what winetricks' `vcrun2022 d3dcompiler_47 d3dx9 d3dx10 d3dx11_43` do, and the
  Visual C++ and `d3dcompiler_47` files are byte for byte the same; winetricks
  isn't needed. It takes a few seconds, and the output goes to
  `.umbra/logs/proton-setup.log`. A prefix set up with protontricks already
  counts as ready. If a Proton update puts one of Wine's stand-ins back, the
  next Play replaces just that file.

**Setup's own tools.** stalker-gamma-cli brings its own git, curl and 7-Zip.
It runs without FUSE (`APPIMAGE_EXTRACT_AND_RUN`), and on a Linux without ICU
with .NET's `DOTNET_SYSTEM_GLOBALIZATION_INVARIANT`. Setup and the launcher
bring their own Python, Tk and OpenSSL: players need nothing installed. The
build checks `Umbra Setup.exe` under Wine in a new, empty prefix with no Python
in it (never the build's own prefix, which has one), and deletes it afterwards.

**Nothing from the build machine.** The programs carry no paths of the machine
that built them (modules are named relative, `umbra_installer/install.py`), and
find everything at run time: Steam from its registry entry on Windows, or its
usual Linux homes (`~/.local/share/Steam`, `~/.steam`, Flathub's
`~/.var/app/com.valvesoftware.Steam`, Ubuntu's Snap `~/snap/steam/common`), the
Downloads folder from Windows' known folders or `XDG_DOWNLOAD_DIR`, and the
Proton prefix from what Steam passes the launcher. The pack builder puts
tokens in place of the build machine's paths and warns about any other
mention of its home folder.

## The launcher

Steam's "Umbra" opens it, and so do the Start menu, the applications menu and
the desktop shortcut (without Steam: see above). The window's class is
`Umbra`, the menu entry's `StartupWMClass`, so docks group it with the entry.
It has:

- **Play**, which starts the game through Mod Organizer 2 without MO2's window
  (`ModOrganizer.exe -p "Umbra" run -e "<entry>"`; MO2 exits with the game).
  The launcher hides while the game runs and comes back when it closes.
- **Renderer**, MO2's Run-list entries that start Anomaly's engine. DirectX 11
  comes first, with the AVX build first when the CPU has AVX (and left out
  when it doesn't). The pick is remembered (`.umbra/launcher.json`).
- **The options** (the season), with **Apply**, which runs Setup's own install
  steps with the new picks. A choice installed before is still on disk, so
  switching back is quick; the launcher says when a pick needs a download.
- **Check for updates**, which reads the channel. It offers **Update** when a
  newer version is out, else **Repair**, which also reinstalls any Umbra mod
  whose folder lost files.
- **Open Mod Organizer 2**, **Credits**, and **Folders**: the game's logs (for
  bug reports), Umbra's logs (Setup's, and the Proton setup's), the MO2 and
  Anomaly folders.
- Before Play and Open MO2, a check that Umbra's engine is still in the
  Anomaly folder (a G.A.M.M.A. update replaces it; the launcher puts it back
  from the download cache), and that what the game needs from Microsoft is in
  place, which it sets up when it isn't (the first start on Linux; see above). If the game still closes right after it starts, the launcher says so
  and where its log is.

It is Umbra Setup itself: Setup copies itself into `.umbra` as
`Umbra Launcher.exe` (Windows) or `umbra-launcher` (Linux), and under that
name it opens as the launcher. Updating and repairing happen in its own
process, never through Steam's files, since Steam is open.

How it starts MO2 differs by system:

- **Windows:** Steam starts the launcher, and the launcher starts
  `ModOrganizer.exe`.
- **Linux:** the launcher runs natively, since Setup's steps need the real
  system rather than Proton's. The shortcut still starts MO2 through Proton,
  and its launch options wrap that command:
  `"<install>/.umbra/umbra-launcher" -- %command%`. The launcher gets Steam's
  whole Proton command after `--` and adds MO2's arguments to it. Started
  outside Steam, it can't play, and says so. If the launch options are
  removed, Steam starts MO2 directly, as before.

## Privacy

Nothing published may contain a machine's paths or an account name.

- The build replaces this machine's MO2, Anomaly and baker paths in text files
  with the tokens above. It lists any other mention of your home folder as a
  warning; fix every warning before publishing.
- `meta.ini` files are rewritten with only the keys MO2 needs, so download
  paths and similar local details are left out.
- `anomaly/appdata/xrrazom_lan_id.bin` is each machine's own co-op identity.
  It is never packed: the build takes only the layers listed in `umbra.toml`,
  never the game's own `appdata` folder.
- `appdata/user.ltx` (graphics, keys, console settings) is specific to one
  machine's hardware. If Umbra ships settings, it ships only a chosen subset.
- Steam account ids are read on the player's own machine to find the right
  Steam files. They never leave it.

## Credits

Umbra is made of other people's work. Every author is listed, with a link to
their mod, in `CREDITS.md`, which the build generates from `pack/credits.toml`
into `dist/`. The installer shows the same list and writes it to
`UMBRA-CREDITS.txt`. If you add a mod, add its author to `pack/credits.toml`
before you build.
